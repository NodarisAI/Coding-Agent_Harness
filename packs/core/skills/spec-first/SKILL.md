# Spec first: turn a sentence into an engineer's brief

The person asking may not know the repository, its commands or what "done" should mean. Your job is to
know. A vague request is not permission for a vague change: it is a request to do the senior engineer's
thinking as well as the typing.

## 1. Discover (read before you write)
1. Take the nouns and verbs of the request and search for them: `grep -rn` for the domain words, the
   screen or endpoint names, the error text. Follow the hits to the owning module.
2. Read the owner, its callers (`grep -rn "<function name>("`), and its existing tests. Note the pattern
   the neighbours follow: how they validate input, check permissions, log, raise errors and test.
3. Read the repository's guides if present: CLAUDE.md, AGENTS.md, CONTRIBUTING.md, DECISIONS.md.
4. Run the existing tests for that area once, so you know the baseline before you change anything.

## 2. Write the brief (in your first message, ten lines or fewer)
- **Problem:** the precise defect or feature, with file and function names.
- **Cause or design:** why it happens, or how the feature fits the existing structure.
- **Acceptance checks:** observable facts a reviewer can verify: a request that returns 403, a test that
  fails before and passes after, a value that no longer appears in a log.
- **Surfaces:** does it touch patient data, tenants, auth, money, uploads or a model? If yes, the
  healthcare-domain and self-attack skills apply.
- **Out of scope:** what you will not change.
- **Decisions:** every choice you made because nobody could answer, and why it is the safest option that
  still delivers the request. Never resolve a risk by quietly shrinking the feature.

### For architectural work, write the spec down
When the change cannot be said in one sentence, touches a migration, an API or cross-repo contract, auth, PHI,
encryption, money or tenant isolation, or is a new application, write `docs/specs/<feature>.md` before code:
- **Requirements** in EARS form, each one testable: "When a user of one tenant requests another tenant's claim, the
  system shall return 404 and record the attempt under the caller's tenant." "While a BAA is expired, the system
  shall refuse PHI processing for that tenant." "If an 835 file contains a delimiter inside a name, then the system
  shall reject the claim with reason code `embedded_delimiter`."
- **Design:** the modules, data model changes, and which existing patterns each part follows.
- **Tasks:** vertical slices in order, each with the test that proves it.
Tick the tasks off in the file as you finish them, so the next person can see where the work stands.

## 3. Use the frameworks the repository already uses
Reach for the established mechanism the stack provides before writing your own:
- **Django / DRF:** permission classes and object-level `has_object_permission`; tenant scoping in the
  queryset (`get_queryset` filtered by the principal's tenant), serializers with explicit `fields`, never
  `__all__`; migrations generated by `makemigrations` and checked with `makemigrations --check`; settings
  through the existing settings module.
- **React / TypeScript:** the existing API client and its types; validation with the schema library the
  repo uses (zod, yup); accessibility through native elements and ARIA patterns from the WAI-ARIA
  Authoring Practices; tests with the existing runner and Testing Library queries by role.
- **Node services:** the existing router's middleware for auth; schema validation at the boundary.
- **Everything:** the repository's own logger, error types and audit helper. If none exists, add one
  small, typed helper next to where it is used and say so.

## 4. Build test-first
Write the test that proves the acceptance check and watch it fail. Make it pass with the smallest change
that follows the neighbours' pattern. Run the area's tests, then the full verify command from the repo
card. The done gate will stop the turn until a check has passed after your last change.

## 5. Summarise for someone who did not watch
What changed and why, the commands you ran with their results, the decisions you made, and what you could
not verify. Plain sentences. No claim you did not check.
