How one sentence becomes production work

A teammate or a practice owner types what they want. They do not name the file, the test command, the threat or the standard. Plain Claude Code works from the sentence as typed. The harness runs every change through the same stages a senior healthcare engineer would, and the stages that matter most are enforced by code, so the model cannot skip them.

  1. UnderstandThe intake hook reads the repository: its stack, its test, lint and type commands, and where the tests live. A request that names no file becomes a written brief with acceptance checks before anything is edited.
  2. ClassifyA request about patients, practices, sign-in, money, uploads or models gets the eight-point security checklist in the model’s context. So does the first edit to a sensitive file, even when the request never said so.
  3. Build on foundationsA new application starts from the blueprint: practice separation, sign-in with MFA, an audit trail, encrypted identifiers, safe logging, bounded input and a verify script, each with its own test.
  4. Lint while writingEvery write is checked for patient fields in log lines and realistic identifiers in test data, and the model is told the line to fix.
  5. AttackThe model attacks its own change under written rules of engagement, and every attack becomes a test that fails on the unsafe version.
  6. Scan and reviewSecret, pattern and dependency scanners run on what changed, and a read-only reviewer agent reads the diff against seven categories.
  7. GateThe turn cannot end until a check passed after the last change and, for sensitive work, until attack tests ran, the scan was clean and a threat model note exists.
  8. ProveThe trust receipt lists what was proven from recorded events, not from the model’s summary.

Self-attack: rules of engagement

  1. This machine only.Attacks run against the local code and tests, on local addresses. Nothing is sent to a shared or production system.
  2. Synthetic data only.Test people have names nobody could mistake for a patient, reserved phone ranges and never-issued identifiers.
  3. Nothing destructive.No deletes outside the test database, no load tests, no scans of other hosts. The destructive-command guard enforces this whatever the model decides.
  4. Every finding is closed.A finding is fixed, or pinned by a test and named for the owner. None is left as a note.
  5. The attacks tried.Another practice’s data, missing or bypassed sign-in, identity fields forged in the request, mass assignment, SQL, X12 and spreadsheet-formula injection, prompt injection into model features, oversized and malformed input, patient data in errors and logs, replay, and money that does not add up.

The eight-point security checklist

  1. Threat model first.Changed endpoints, every kind of caller, the trust boundary and at least three abuse cases, each mapped to its test.
  2. Identity from the signed-in user.Practice, user and actor ids sent in a request are derived from the principal or rejected.
  3. Every layer enforces.The view, the service, the query and the policy engine, not only the nearest one.
  4. Refusals are audited.A denied attempt is recorded against the caller’s real practice, with no patient data in the record.
  5. Uniform errors.A refusal never reveals whether the other practice or record exists.
  6. Service callers still work.Background jobs and service accounts on the same path are tested too.
  7. Bounded and fail-closed.Sizes, counts and lengths are limited; errors are typed; nothing is silently repaired.
  8. Attack, scan, review.Then fix what they find.

Redaction, on a synthetic error log and remittance

Before a log, an error or an X12 file leaves the machine, tools/redact.py replaces each identifier with a pseudonym. One value keeps one pseudonym everywhere it appears, so the member id in the log line and in the remittance still match, and the amounts and adjustment codes stay readable. When the tool cannot vouch for the result, it writes nothing.

Installing it on a teammate’s machine

The team build is a separate Claude Code configuration folder. It carries the pipeline, the secret and destructive-command guards, 75 deny rules, nine skills and the rules file, and nothing from the machine it was built on. It runs beside a normal Claude Code setup without changing it.

What it buys, and what it costs

The harness is not free. Every benefit on the left has a price on the right, and the benchmark has not yet shown a quality lead.

What it buys

  1. Risky actions are stopped by code, not by asking nicely.Four guard hooks and 109 deny rules run before a tool call, whatever the model believes. Secrets and patient data are refused mechanically.
  2. A mistake is fixed once.Lessons are recalled on every prompt and the first time a file is opened, and every finished session is queued so new lessons can be mined from it.
  3. “Done” has to be shown.The definition of done asks for every requirement mapped to a test or a file, with real check output quoted. It targets the failure the benchmark saw most: summaries that claimed more than the code did (2 cases for the harness, 3 for plain).
  4. Known methods for known work.Nine engineering skills bring playbooks for security, test-first building, triage, agent reliability and launch audits.
  5. Long sessions keep every request.Your requests, the to-do list and unresolved failures survive compaction word for word.
  6. It stays out of the way.The guards blocked none of 713 tool calls in the benchmark, and the harness never refuses an ordinary request. When a person must decide, it asks once.

What it costs

  1. More reading on every turn.The first turn reads 24,000 to 44,000 tokens against plain’s 19,000 to 39,000: about 5,000 more, and the rules and recalled lessons stay in the context.
  2. A little latency.The hooks add about 50 ms to a tool call, and 92 ms at worst.
  3. Slower on hard tasks.In round 2 the harness took 27% longer on five hard reruns: 7,735 seconds against 6,108.
  4. No quality lead yet.189 against 191 points over 15 blind-judged pairs is a tie within the judge’s own noise, and the judge would have merged the plain result on both round-3 tasks.
  5. Friction by design.A guard can stop a harmless command that looks risky. During setup, the push rules first flagged about a dozen harmless commands before they were tuned.
  6. More to maintain.Nine hook scripts, nine skills and 109 rules must stay correct as Claude Code changes. A heavier personal setup lost its first test 8 to 10 and ran about 50% slower, which is why the pack is a slim subset.

What the benchmark says so far

Eight tasks on three real Nodaris repositories (SMCP, AROS and NDE), from easy fixes to security and architecture work. Each task runs through both setups in separate clones. A separate model grades both against a hidden rubric without knowing which is which: 10 core checks and 5 stretch checks per task.

So far it is a tie on quality. What the harness adds today is safety and memory; what it costs is context, a little latency and time on hard tasks. The loop continues: every lost point becomes a rule, and rounds repeat until the harness wins two in a row.

Before this loop, the full personal setup (every plugin, hook and memory system) lost its first test 8 to 10 and took 1,295 seconds against 859. The pack keeps only the parts that earn their cost. The judge’s scores move by two to three points between runs, so a single round decides nothing.
